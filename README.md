# RAG-поиск по документам предприятия

Локальная система вопросов и ответов по внутренним документам (приказы, положения, инструкции)
с поиском противоречий между ними. Работает полностью офлайн на CPU, без GPU,
рассчитана на ПК уровня **Intel i3-12100 / 8 ГБ ОЗУ**.

Что умеет:

- **Загрузка PDF**: текстовый слой через PyMuPDF; сканы распознаются Tesseract OCR (русский + английский).
- **SQL-источник**: подтягивает уже распарсенные документы из базы (PostgreSQL, MS SQL, MySQL, SQLite).
- **Автозагрузка из папки**: PDF из сетевой папки подхватываются сами раз в 5 минут.
- **Вопрос–ответ** с указанием источников `[1]`, `[2]`: номер, дата и страница документа.
  Интерфейс в виде чата: ответ приходит целиком, коротко (1–2 предложения), под ним только те документы,
  из которых он взят, и противоречия, касающиеся именно их. Галочка «подробно» включает развёрнутый ответ.
- **Поиск противоречий** между документами. Пример: «запрещено пользоваться техникой Apple» и
  «фотофиксацию вести только на iPhone». Каждый новый документ проверяется против базы автоматически;
  найденные конфликты можно подтвердить или отклонить.
- **Проверка проекта документа** до подписания: вставьте текст нового приказа, и система покажет,
  с какими действующими документами он конфликтует.
- Номер и дата документа извлекаются из шапки, так что в конфликте видно, какой документ новее.

## Как это устроено

```
PDF / SQL / папка ──► извлечение текста (+OCR) ──► фрагменты ~900 символов ──► эмбеддинги bge-m3
                                                                                │
                                                       SQLite (документы, фрагменты, векторы)
                                                                                │
Вопрос ──► гибридный поиск: векторы + BM25 ──► 5 лучших фрагментов ──► LLM (qwen3:4b) ──► ответ с источниками
                                                                                │
Противоречия: похожие по смыслу фрагменты из РАЗНЫХ документов, содержащие требования
(«запрещено», «только», «обязан», сроки…) ──► LLM сравнивает пару и отвечает по JSON-схеме
```

- **LLM**: `qwen3:4b` через Ollama (лицензия Apache 2.0, коммерческое использование разрешено), режим «размышлений» выключен ради скорости.
- **Эмбеддинги**: `bge-m3` (MIT), хорошо понимает русский.
- **Хранилище**: один файл SQLite в `data/`, векторы ищутся в памяти (numpy). Отдельная векторная БД не нужна:
  10 000 фрагментов занимают ~40 МБ.
- **Поиск противоречий** экономит CPU: модель видит только пары, которые похожи по смыслу,
  взяты из разных документов и содержат требования. Уже проверенные пары повторно не проверяются.

## Инструменты

Все компоненты бесплатные, работают локально и не требуют GPU.

**Модели (запускаются через Ollama)**

| Инструмент | Зачем | Лицензия |
|---|---|---|
| [Ollama](https://ollama.com) | локальный сервер моделей: скачивает их, держит в памяти и отвечает по HTTP API | MIT |
| `qwen3:4b` (Alibaba Qwen) | языковая модель: формулирует ответы и сравнивает фрагменты на противоречия | Apache 2.0 |
| `qwen2.5:1.5b` (Alibaba Qwen) | запасная лёгкая языковая модель для слабых ПК | Apache 2.0 |
| `bge-m3` (BAAI) | модель эмбеддингов: превращает текст в векторы для поиска по смыслу, хорошо понимает русский | MIT |

**Приложение (Python 3.12)**

| Инструмент | Зачем | Лицензия |
|---|---|---|
| FastAPI + Uvicorn | веб-сервер: HTTP API и страница интерфейса | MIT / BSD |
| PyMuPDF | извлекает текст из PDF и запускает OCR для страниц без текстового слоя | AGPL-3.0 |
| Tesseract OCR (`rus`, `eng`) | распознаёт текст на сканах | Apache 2.0 |
| SQLite | хранит документы, фрагменты, векторы и найденные противоречия в одном файле | public domain |
| NumPy | векторный поиск в памяти (косинусное сходство) | BSD |
| BM25 (свой код в `app/search.py`) | поиск по словам; дополняет векторный поиск номерами, кодами, точными терминами | — |
| SQLAlchemy | подключение к внешней SQL-базе с уже распарсенными документами | MIT |
| httpx | HTTP-клиент для обращений к Ollama | BSD |
| HTML + JavaScript без фреймворков | интерфейс: чат, документы, противоречия, проверка проекта | — |

**Развёртывание и тесты**

| Инструмент | Зачем |
|---|---|
| Docker, Docker Compose | три контейнера: `ollama` (модели), `ollama-pull` (разово скачивает модели), `app` (приложение) |
| pytest | сквозные тесты на поддельной Ollama (`tests/fake_ollama.py`) |

> PyMuPDF распространяется под AGPL. Для внутреннего использования на заводе это не ограничение;
> если систему будут продавать или отдавать наружу, нужна коммерческая лицензия Artifex
> или замена на `pypdf` (лицензия BSD, но без встроенного OCR).

## Как работает, по шагам

1. **Загрузка.** PDF приходит через интерфейс, из папки `inbox/` или из SQL-базы. Повтор того же файла
   распознаётся по хешу и игнорируется.
2. **Извлечение текста.** PyMuPDF читает текстовый слой. Если на странице меньше 30 символов, это скан:
   страница отправляется в Tesseract. Из шапки регулярными выражениями берутся номер и дата документа.
3. **Разбиение.** Текст режется на фрагменты около 900 символов с перекрытием 150 символов, чтобы мысль
   не обрывалась на границе. Фрагменты с требованиями («запрещено», «только», «обязан», сроки) помечаются отдельно.
4. **Индексация.** bge-m3 превращает каждый фрагмент в вектор, вектор сохраняется в SQLite.
5. **Вопрос.** Вопрос тоже превращается в вектор. Ищутся фрагменты, близкие по смыслу (векторы)
   и по словам (BM25), списки объединяются методом RRF. Пять лучших фрагментов уходят в qwen3:4b.
6. **Ответ.** Модель отвечает строго по JSON-схеме: текст ответа, номера фрагментов, из которых он взят,
   и замечание о противоречии. В чате показываются ответ, только использованные источники
   и противоречия, затрагивающие именно их.
7. **Противоречия.** После загрузки документа его фрагменты с требованиями сравниваются с похожими
   фрагментами других документов. Каждую пару проверяет qwen3:4b и тоже отвечает по JSON-схеме.
   Найденное сохраняется; уже проверенные пары повторно не проверяются.

## Требования к памяти (8 ГБ)

| Компонент | ОЗУ |
|---|---|
| qwen3:4b (Q4) + контекст 4096 | ~3 ГБ |
| bge-m3 | ~1.2 ГБ |
| приложение + OCR | ~0.3–0.5 ГБ |
| ОС + Docker | ~1.5 ГБ |

**Запасная модель.** Вместе с основной скачивается лёгкая `qwen2.5:1.5b` (~1 ГБ, Apache 2.0), и она уже есть
в офлайн-комплекте. Если ПК не тянет qwen3:4b, в `.env` поменяйте одну строку и перезапустите, пересобирать ничего не нужно:

```bash
LLM_MODEL=qwen2.5:1.5b
docker compose up -d
```

Лёгкая модель отвечает примерно вдвое быстрее и занимает вдвое меньше памяти, но хуже понимает сложные
формулировки и чаще ошибается в противоречиях. Вернуть основную: `LLM_MODEL=qwen3:4b` и снова `docker compose up -d`.

> `qwen2.5:3b` по качеству подошла бы, но у неё лицензия Qwen Research (только некоммерческое использование),
> поэтому для завода она не выбрана.

**Скорость на i3-12100** (оценка, нужно замерить на месте): ответ на вопрос 15–60 секунд. Проверка одной пары на противоречие занимает 10–20 секунд, поэтому полная проверка
большой базы — фоновая задача (её можно запустить на ночь). Индексация: порядка 1–3 страниц в секунду.

## Запуск

Нужны Docker и Docker Compose v2.24+.

```bash
cp .env.example .env
docker compose up -d --build
docker compose logs -f ollama-pull   # первый раз скачиваются модели (~3.5 ГБ) в папку models/
```

Откройте http://localhost:8000 (или `http://<ip-пк>:8000` из сети завода).

Положить PDF можно тремя способами:
1. Вкладка «Документы» → «Загрузить».
2. Скопировать файлы в папку `inbox/` (или указать свою папку в `WATCH_HOST_DIR`, например сетевой диск).
3. Настроить `SQL_SOURCE_URL` и нажать «Синхронизировать SQL».

Тестовые приказы с заведомыми противоречиями:

```bash
pip install pymupdf && python scripts/make_sample_pdfs.py   # создаст samples/*.pdf
```

Загрузите их, и во вкладке «Противоречия» должны появиться две пары: Apple (приказы 12 и 47) и
сроки подачи заявления на отпуск (14 и 30 дней).

## Установка без интернета (на заводе)

На заводском ПК нужен **только Docker**: Python, библиотеки, Tesseract и Ollama уже лежат внутри образов.
Модели и образы готовятся заранее на любой машине с интернетом и переносятся вместе с папкой проекта.

**1. На машине с интернетом** (Mac или Linux с Docker):

```bash
bash scripts/make_offline_bundle.sh
```

Скрипт скачивает модели в папку `models/` (~4.7 ГБ, включая запасную), собирает образы под Intel (`linux/amd64`, даже на Mac с M-процессором)
и сохраняет их в `offline/rag-app.tar` (~0.5 ГБ) и `offline/ollama.tar` (~3.8 ГБ). Вместе с моделями
получается около 9 ГБ. Скопируйте всю папку проекта на флешку или сетевой диск.

**2. На заводском ПК:**

```bash
docker load -i offline/rag-app.tar
docker load -i offline/ollama.tar
docker compose up -d --no-build
```

Контейнер `ollama-pull` увидит, что модели уже лежат в `models/`, и завершится, не обращаясь в интернет.
Откройте http://localhost:8000.

**Установка самого Docker без интернета:**
- **Linux** (лучший вариант для сервера): скачайте `.deb`/`.rpm` пакеты Docker Engine и плагина compose
  с download.docker.com на машине с интернетом и установите их на заводском ПК. Docker Engine бесплатен.
- **Windows**: установщик Docker Desktop работает офлайн, но ему нужен WSL 2, который тоже ставится заранее
  (`wsl --update` на машине с интернетом не поможет, нужен офлайн-пакет WSL `.msi` с GitHub Microsoft).
  Docker Desktop бесплатен только для компаний до 250 сотрудников и до $10 млн выручки; для крупного завода
  нужна платная подписка либо Linux.

**Обновление:** замените папку проекта (кроме `data/` и `models/`), заново выполните шаг 1 на машине с интернетом
и `docker load` + `docker compose up -d --no-build` на заводе. Документы и база в `data/` сохранятся.

## SQL-источник

В `.env`:

```
SQL_SOURCE_URL=postgresql+psycopg://user:pass@db-host:5432/docs
SQL_SOURCE_QUERY=SELECT id, title, text, doc_date, doc_number FROM documents
```

Запрос должен вернуть колонки `id`, `title`, `text`, а `doc_date` и `doc_number` необязательны.
Если документ хранится несколькими строками (по страницам или пунктам), верните одинаковый `id`:
строки склеятся. Драйвер БД раскомментируйте в `requirements.txt` и пересоберите образ.
При повторной синхронизации переиндексируются только изменившиеся документы.

## Настройки

Все настройки лежат в `.env` (см. `.env.example`). Главные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_MODEL` | `qwen3:4b` | модель для ответов и проверки противоречий |
| `LLM_MODEL_LITE` | `qwen2.5:1.5b` | запасная лёгкая модель, скачивается заранее; включается через `LLM_MODEL` |
| `EMBED_MODEL` | `bge-m3` | модель эмбеддингов (после смены нужно перезагрузить документы) |
| `TOP_K` | 5 | сколько фрагментов передавать модели |
| `ANSWER_DETAILED` | false | краткие ответы по умолчанию; `true` — подробные |
| `ANSWER_MAX_TOKENS` | 250 | предел длины краткого ответа |
| `LLM_THINK` | false | режим рассуждений Qwen3; включать не советую — на CPU в разы медленнее |
| `LLM_NUM_CTX` | 4096 | размер контекста; больше — медленнее и больше памяти |
| `CONTRA_SIM_THRESHOLD` | 0.55 | порог сходства для пары-кандидата; ниже — полнее, но дольше |
| `CONTRA_MAX_PAIRS` | 300 | максимум пар за одну проверку; остальные дойдут при следующем запуске |
| `CONTRA_AUTO` | true | проверять каждый новый документ автоматически |
| `OCR_ENABLED` | true | распознавать сканы |

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | доступность Ollama и наличие моделей |
| GET/POST | `/api/documents` | список / загрузка PDF (multipart `files`) |
| DELETE | `/api/documents/{id}` | удалить документ |
| POST | `/api/ask` | `{"question": "...", "detailed": false}` → `{answer, sources, contradictions}`: ответ целиком, только использованные источники и противоречия по ним |
| POST | `/api/search` | только поиск фрагментов, без LLM |
| GET | `/api/contradictions` | найденные противоречия (`?status=new|confirmed|dismissed`) |
| POST | `/api/contradictions/scan` | запустить проверку (`{"doc_ids": [..]}` или все документы) |
| GET | `/api/contradictions/status` | прогресс проверки |
| POST | `/api/check` | проверить проект документа (`text` или `file`) против базы |
| POST | `/api/sql/sync` | синхронизация с SQL-источником |

Документация Swagger: http://localhost:8000/docs

## Разработка и тесты

```bash
pip install -r requirements.txt pytest
python scripts/make_sample_pdfs.py
python -m pytest tests -q
```

Тесты используют поддельную Ollama (`tests/fake_ollama.py`): они проверяют загрузку, OCR, индекс, API,
SQL-источник и хранение противоречий, но не качество модели. Качество нужно проверять на реальных документах.

## Частые проблемы

- **«model "bge-m3" not found» / статус «ждёт модель».** Модели ещё скачиваются (первый запуск).
  Ход загрузки: `docker compose logs -f ollama-pull`. Документы подождут и обработаются сами,
  как только модель появится. Документ в статусе «ошибка» можно перезапустить кнопкой «повторить».
- **Вверху справа «не скачаны модели».** Загрузка прервалась: запустите `docker compose up -d ollama-pull`
  или вручную `docker compose exec ollama ollama pull bge-m3`.

## Ограничения

- Маленькая модель иногда ошибается: пропускает противоречия, требующие знаний о мире (например,
  что iPhone — это Apple), или находит ложные. Поэтому каждое противоречие можно подтвердить или отклонить.
- Таблицы в PDF извлекаются как текст, без структуры.
- Качество OCR зависит от скана: лучше всего работает при 300 dpi.
- Доступ к интерфейсу без авторизации, так что открывайте порт только во внутренней сети.
